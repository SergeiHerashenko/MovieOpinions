### Зафіксовані робочі правила

- [x] Використовується послідовність `validate/prepare -> approve -> apply -> record events and changes`.
- [x] `Result` використовується для очікуваних бізнес-відмов, які може спричинити коректний зовнішній запит.
- [x] Domain exceptions використовуються для порушеного внутрішнього контракту або неможливого збереженого стану.
- [x] Домен сам захищає свої інваріанти, навіть якщо Application уже виконувала власні перевірки.
- [x] Один timestamp отримується Application на початку use case та передається через увесь доменний виклик як стабільне значення.
- [x] Часова істина не делегується background job: домен сам визначає, чи є сесія чинною на переданий `now`.
- [x] `IEnumerable<T>` використовується для послідовного перебору; `IReadOnlyCollection<T>` — коли потрібен ще й `Count`; `IReadOnlyList<T>` — коли потрібен індекс.
- [x] `ToArray` / `ToList` матеріалізують LINQ-запит; вибір між ними залежить від потрібного контракту й подальших операцій, а не сам по собі від «валідації» чи «мутації».
- [x] Відкладене виконання LINQ враховується: без матеріалізації запит читає актуальний стан у момент фактичного перебору.
- [x] Узгоджено семантику `Where`, `Select`, `Any`, `All`, `FirstOrDefault` та `SingleOrDefault`.
- [x] Абстракції й поліморфні plan-класи вводяться після появи реальної варіативної поведінки, а не наперед заради кількох рядків.
