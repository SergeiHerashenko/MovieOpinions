# Зроблено сьогодні (14 вересня 2026)

### DomainGuard і правила внутрішньої консистентності

- [x] Додано `DomainGuard.AgainstEarlierThan<TContext>` для перевірки, що час доменної операції не передує мінімально допустимому часу.
- [x] Часова перевірка отримує `OperationType`, назви обох полів та додає мінімально допустиме значення до діагностичного контексту exception.
- [x] Зафіксовано, що `AgainstEarlierThan` дозволяє рівність; інваріанти, які потребують строго пізнішого часу, перевіряються окремо через `<=`.
- [x] Додано `DomainGuard.AgainstUndefinedEnum<TEntity>` для централізованої перевірки одного або декількох enum-полів.
- [x] Невідоме enum-значення трактується як внутрішня неузгодженість і призводить до `UnsupportedDiscriminator`.
- [x] Зафіксовано правило: закриті низькорівневі методи, які отримують уже перевірені доменні об’єкти від власного коду, кидають exception у разі порушення внутрішнього контракту.
- [x] Очікувані бізнес-відмови у доступній поведінці продовжують повертатися через `Result`.

### Уніфікація доменної валідації

- [x] `ValidationFailure` об’єднує два представлення порушеного правила: очікуваний `Error` і фабрику `Func<OperationType, Exception>`.
- [x] Правила валідації не кидають exception самостійно, а лише описують виявлене порушення.
- [x] Exception створюється відкладено через `BuildException` і фактично кидається лише оператором `throw`.
- [x] Додано `ValidationRulesFailure<TFailure>`, який містить рівно одне типізоване значення результату валідації.
- [x] Конкретні валідатори надають окремі методи `ValidateForError` і `ValidateForException`.
- [x] `Create` отримує лише `Error` і повертає `Result`, а `Restore` отримує лише `Exception`.
- [x] Набір правил та `ValidationOrchestrator` приховано всередині `internal static partial` валідатора.
- [x] Окремі правила оформлено як приватні вкладені класи, тому їх неможливо викликати напряму поза валідатором.
- [x] Від базового універсального класу валідатора поки відмовилися; рішення відкладено до появи підтвердженої потреби після завершення Domain.
- [x] Зафіксовано підхід до коментарів: XML-документація описує контракт, а inline-коментарі пояснюють лише неочевидні причини та інваріанти.

### Зміна стану UserRestrictionSession

- [x] `AddRestrictions` оформлено як strict internal-метод, що кидає exception у разі порушення контракту між `User` і session.
- [x] Метод відхиляє null, порожній набір, null-елементи, іншого користувача, інший тип, дублікати у вхідному наборі та вже наявні ID.
- [x] Перевірка і розрахунок виконуються до зміни стану session, тому помилка не залишає entity частково оновленою.
- [x] Для накопичення хвилин і нового загального значення використовується `checked`.
- [x] Після успішної перевірки нові ID додаються через `UnionWith`, а загальна тривалість оновлюється одним кроком.
- [x] `RemoveRestriction` перевіряє власника, тип і наявність restriction ID у session.
- [x] Перед видаленням обчислюється потенційний новий стан без передчасної мутації entity.
- [x] Допустимими результатами видалення є лише порожня session з нульовими хвилинами або непорожня session з додатною кількістю хвилин.
- [x] Неузгоджений результат видалення призводить до `DomainInvariantViolationException`.
- [x] Порожня session видаляється агрегатом `User`, а не залишає невалідний persistence-запис.
